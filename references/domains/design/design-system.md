# 设计系统细分模块

> 领域模块六节 Schema：领域画像 / 细分路由 / 预设知识骨架 / 权威信源清单 / 进阶检查点 / 常见误区。

## ① 领域画像

设计系统把设计规范、组件资产与工程实现融为一体：Design Token、组件库、文档与治理机制。核心价值是**"让团队用同一套语言协作"**——设计系统不是组件库的别名，而是持续演进的产品。

## ② 细分路由

本模块即最小细分单位，不再下分。

## ③ 预设知识骨架

建模（P2）以此树为起点，按用户目标层级裁剪（规则见 `references/core/modeling.md`）。每个叶子节点括注掌握证据。

```
设计系统
├── L1 基础层
│   ├── 设计系统组成（Token/组件/文档/治理四件套，能说清各自职责）
│   ├── 设计原则与规范制定（为什么规范不是拍脑袋；能为一个组件或页面写出原则、适用条件和可检查的例子）
│   └── 原子设计理论（原子-分子-组织-模板-页面的层次映射；能把一组实际界面资产映射到各层级，并解释一个边界案例的取舍）
├── L2 视觉规范
│   ├── Design Token（颜色/字号/间距/圆角/阴影的体系化命名；能为一组组件定义有语义层级的 Token 命名，并演示主题切换时哪些值继承、哪些值覆盖）
│   └── 图标系统（图标网格、风格统一、多规格输出；能按网格、笔画和尺寸规则检查一组图标并指出不一致项）
├── L3 组件层
│   ├── 组件设计（状态/变体/API 的完整定义，能设计一个可复用组件）
│   ├── 模式库（Patterns：表单/表格/筛选的组合范式；能为一个真实任务整理表单、表格或筛选模式，标注适用条件、空错状态和例外场景）
│   └── 文档编写（Do/Don't、可访问性说明、使用示例；能为一个组件写出使用条件、Do/Don’t、可访问性要求和可复现示例）
├── L4 工程落地
│   ├── 与前端组件库对齐（Token 到 CSS 变量的映射、单一事实源；能把一组设计 Token 映射到 CSS 变量或组件属性，并演示单一事实源如何同步变更）
│   └── 版本与变更管理（breaking change 的沟通与迁移；能为一次破坏性变更写出影响范围、迁移步骤、兼容窗口和回滚方案）
└── L5 治理层
    ├── 采纳度度量（组件使用率、绕过率的数据监测；能定义组件使用率与绕过率的口径，给出埋点字段和一个可复核的采纳度报表草案）
    └── 多品牌/多端主题（Token 分层支持主题化；能为两个品牌或平台建立 Token 分层示例，说明共享层、覆盖层及视觉回归检查点）
```

## ④ 权威信源清单

| 级别 | 信源 | 备注 |
|---|---|---|
| 书籍 | 《Atomic Design》（Brad Frost） | L1 方法论源头 |
| 官方 | Material Design / Ant Design / TDesign 设计体系 | 可直接研究的完整范本【时效敏感】 |
| 社区 | Design Systems 社区（designsystems.com）、Figma 官方博客 | 案例与治理经验 |
| 实践 | 为自家产品搭建一套 Token + 组件 + 文档 | 最有效的学习方式之一 |

## ⑤ 进阶检查点

| 阶段 | 能力证据（能做成这些即过关） |
|---|---|
| 初级（L1–L2） | 为一套界面梳理完整 Token 体系；编写一个组件的完整文档（含 Do/Don't） |
| 中级（L3–L4） | 设计并落地覆盖高频场景和常见状态的组件库（与前端 API 对齐）；完成一次版本升级与迁移说明 |
| 高级（L5） | 主导设计系统建设与治理（采纳度提升）；支持多品牌主题化方案 |

## ⑥ 常见误区

1. **只管组件不管治理**：组件库建完没人用，没有治理机制的设计系统是摆设。
2. **文档滞后于实现**：组件更新文档不更新，信任一旦崩塌就再也建不回来。
3. **设计与实现两张皮**：Figma 里的组件和代码里的组件 API 不一致，协作成本反而增加。
4. **追求大而全**：第一版就想覆盖所有场景，结果两年上不了线，从最高频组件开始。
5. **忽视可访问性**：组件不带键盘焦点与对比度设计，设计系统会系统性放大体验缺陷。
