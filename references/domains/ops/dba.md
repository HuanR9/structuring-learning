# DBA（数据库运维）细分模块

> 领域模块六节 Schema：领域画像 / 细分路由 / 预设知识骨架 / 权威信源清单 / 进阶检查点 / 常见误区。

## ① 领域画像

DBA 负责数据库的可用、性能与安全：安装部署、备份恢复、高可用、性能优化、容量规划、故障处置。核心价值是**"数据不丢、服务不挂、查询不慢"**。学习路径以 MySQL 为主线（国内主流），再横向扩展。

## ② 细分路由

本模块即最小细分单位，不再下分。生态扩展（Redis / PostgreSQL / MongoDB）作为 L6 可选分支处理。

## ③ 预设知识骨架

建模（P2）以此树为起点，按用户目标层级裁剪（规则见 `references/core/modeling.md`）。每个叶子节点括注掌握证据。

```
DBA
├── L1 基础层
│   ├── SQL 精通（能写多表关联/子查询/窗口函数，能用执行计划验证写法差异）
│   ├── 关系模型与范式（能判断一张表设计是否违反三范式、何时反范式）
│   ├── 索引原理（B+ 树结构、最左前缀、覆盖索引、回表——能手画并解释）
│   └── 事务与隔离级别（ACID、四种隔离级别、各自解决的并发问题与代价）
├── L2 引擎层（MySQL）
│   ├── MySQL 体系结构（连接器/Server 层/引擎层的职责划分）
│   ├── InnoDB 存储结构（页/区/段、缓冲池、change buffer）
│   ├── 锁机制（行锁/间隙锁/表锁/MVCC，能分析死锁日志）
│   └── 日志体系（redo/undo/binlog 各自作用与刷盘策略、两阶段提交）
├── L3 运维层
│   ├── 安装部署与参数配置（关键参数含义与调优方向）
│   ├── 备份恢复（逻辑/物理备份取舍、PITR 时点恢复实操）
│   ├── 主从复制（异步/半同步/GTID，能排查延迟与中断）
│   ├── 高可用方案（MHA/Orchestrator/InnoDB Cluster 的选型与局限）
│   └── 监控告警（核心指标体系：连接/QPS/慢查询/复制延迟/锁等待）
├── L4 性能层
│   ├── 执行计划解读（EXPLAIN 各列含义、type 全档位判断）
│   ├── 慢查询治理（慢日志分析、索引优化、SQL 重写套路）
│   ├── 索引优化实战（联合索引设计、索引下推、隐式转换坑）
│   └── 容量规划（单表行数经验值、分表时机判断）
├── L5 架构层
│   ├── 分库分表（垂直/水平拆分、全局 ID、跨片查询代价）
│   ├── 读写分离（一致性代价与适用场景）
│   ├── 中间件（ShardingSphere/MyCat 原理与边界）
│   └── 容灾设计（同城双活/异地多活的 RPO/RTO 权衡）
└── L6 扩展生态（可选分支，按需选修）
    ├── Redis（数据结构选型、持久化、缓存三大问题）
    ├── PostgreSQL（与 MySQL 的架构差异）
    └── MongoDB（文档模型适用场景）
```

## ⑤ 进阶检查点

| 阶段 | 能力证据（能做成这些即过关） |
|---|---|
| 初级（L1–L2） | 手画 InnoDB 架构与 B+ 树；分析一个死锁案例；解释一条慢 SQL 的执行计划 |
| 中级（L3–L4） | 独立完成备份恢复演练（含 PITR）；搭建主从并人工注入故障后修复；将一条慢查询优化一个数量级 |
| 高级（L5） | 为一个给定业务设计分库分表或高可用方案并写出取舍分析；主导一次数据库故障复盘 |

## ⑥ 常见误区

1. **只背参数不懂原理**：参数调优建立在理解引擎机制上，背参数表无效。
2. **跳过 L1 直接学运维**：SQL 与索引原理不过关，后面全部悬空。
3. **只看不做**：备份恢复、主从切换必须亲手演练，看十遍不如做一次。
4. **版本混淆**：MySQL 5.7 与 8.0 差异大（如默认引擎细节、窗口函数），学习资料先核对版本。
5. **忽视业务语境**：高可用/分库分表是权衡题不是标准答案，脱离业务规模和 RPO/RTO 谈方案没有意义。
