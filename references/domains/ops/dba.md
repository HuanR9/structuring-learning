# DBA（数据库运维）细分模块

> 领域模块六节 Schema：领域画像 / 细分路由 / 预设知识骨架 / 权威信源清单 / 进阶检查点 / 常见误区。

## ① 领域画像

DBA 负责数据库的可用、性能与安全：安装部署、备份恢复、高可用、性能优化、容量规划、故障处置。核心价值是**"数据不丢、服务不挂、查询不慢"**。以用户目标或现有生产数据库为主线；没有指定时可用 MySQL 举例，不把它假定为所有团队的默认技术栈。

## ② 细分路由

本模块即最小细分单位，不再下分。生态扩展（Redis / PostgreSQL / MongoDB）作为 L6 可选分支处理。

## ③ 预设知识骨架

建模（P2）以此树为起点，按用户目标层级裁剪（规则见 `references/core/modeling.md`）。每个叶子节点括注掌握证据。

```
DBA
├── L1 基础层
│   ├── SQL 精通（能写多表关联/子查询/窗口函数，能用执行计划验证写法差异）
│   ├── 关系模型与范式（能判断一张表设计是否违反三范式、何时反范式）
│   ├── 索引原理（B+ 树结构、最左前缀、覆盖索引、回表——能手画并解释）
│   └── 事务与隔离级别（ACID、四种隔离级别、各自解决的并发问题与代价；能用并发事务时间线复现脏读、不可重复读或幻读等现象，并解释隔离级别带来的取舍）
├── L2 数据库引擎层（按目标数据库选型；未指定时以 MySQL 作示例）
│   ├── MySQL 体系结构（连接器/Server 层/引擎层的职责划分；能从客户端请求画出 MySQL 各层处理路径，指出解析、优化、执行和存储引擎的职责边界）
│   ├── InnoDB 存储结构（页/区/段、缓冲池、change buffer；能画出页、区、段和缓冲池之间的关系，并用一个读写案例说明数据页如何进入内存）
│   ├── 锁机制（行锁/间隙锁/表锁/MVCC，能分析死锁日志）
│   └── 日志体系（redo/undo/binlog 各自作用与刷盘策略、两阶段提交；能在隔离实例演示日志各自承担的恢复/复制职责，说明崩溃恢复时序和关键验证点）
├── L3 运维层
│   ├── 安装部署与参数配置（关键参数含义与调优方向；能在测试实例完成部署并调整一项参数，用基线对比证明效果且提交恢复默认值步骤）
│   ├── 备份恢复（逻辑/物理备份取舍、PITR 时点恢复实操；能对隔离数据库执行备份与 PITR 恢复，核对目标时间点数据并记录 RPO/RTO 实测值）
│   ├── 主从复制（异步/半同步/GTID，能排查延迟与中断）
│   ├── 高可用方案（MHA/Orchestrator/InnoDB Cluster 的选型与局限；能在非生产环境演练一次主节点故障切换，记录数据丢失/恢复时间并比较方案限制）
│   └── 监控告警（核心指标体系：连接/QPS/慢查询/复制延迟/锁等待；能为连接、慢查询、复制延迟和锁等待定义查询/告警口径，并用样例阈值验证告警）
├── L4 性能层
│   ├── 执行计划解读（EXPLAIN 各列含义与访问路径；能从样例查询计划识别主要访问路径和估算行数，并提出验证估算偏差的方法）
│   ├── 慢查询治理（慢日志分析、索引优化、SQL 重写套路；能分析一条慢日志和执行计划，提交优化前后查询计划/耗时及结果一致性验证）
│   ├── 索引优化实战（联合索引设计、索引下推、隐式转换坑；能按读写模式设计或调整索引，用执行计划和样例负载验证收益及写入维护代价）
│   └── 容量规划（数据增长、存储和资源趋势；能用业务增长假设估算容量与复核时间点，解释分区或拆分决策对查询、维护和恢复的影响）
├── L5 架构层
│   ├── 分库分表（垂直/水平拆分、全局 ID、跨片查询代价；能按访问模式选择分片键，模拟跨片查询和扩容迁移，量化路由、事务与维护代价）
│   ├── 读写分离（一致性代价与适用场景；能用复制延迟案例比较一致性读策略，设计读写路由规则并验证读己之写边界）
│   ├── 中间件（ShardingSphere/MyCat 原理与边界；能跟踪一条分片 SQL 的路由和改写过程，验证边界查询并列出中间件接管不了的场景）
│   └── 容灾设计（同城双活/异地多活的 RPO/RTO 权衡；能根据业务连续性目标比较恢复方案，定义验证步骤、数据一致性风险和切回条件）
└── L6 扩展生态（可选分支，按需选修）
    ├── Redis（数据结构选型、持久化、缓存三大问题；能按访问模式比较 Redis 数据结构，完成小型缓存/持久化实验并验证穿透、击穿或雪崩防护）
    ├── PostgreSQL（与 MySQL 的架构差异；能用同一查询场景比较 PostgreSQL 与 MySQL 的执行计划或事务行为，写出适用条件而非绝对优劣）
    └── MongoDB（文档模型适用场景；能为一个文档型场景设计文档结构和索引，用样例查询验证读写路径及反范式化代价）
```

## ⑤ 进阶检查点

| 阶段 | 能力证据（能做成这些即过关） |
|---|---|
| 初级（L1–L2） | 手画 InnoDB 架构与 B+ 树；分析一个死锁案例；解释一条慢 SQL 的执行计划 |
| 中级（L3–L4） | 独立完成备份恢复演练（含 PITR）；在隔离环境搭建复制并演练故障恢复；优化一条代表性慢查询，验证结果一致并解释性能变化及适用负载 |
| 高级（L5） | 为一个给定业务设计分库分表或高可用方案并写出取舍分析；主导一次数据库故障复盘 |

## ⑥ 常见误区

1. **只背参数不懂原理**：参数调优建立在理解引擎机制上，背参数表无效。
2. **跳过 L1 直接学运维**：SQL 与索引原理不过关，后面全部悬空。
3. **只看不做**：备份恢复、主从切换必须亲手演练，看十遍不如做一次。
4. **版本混淆**：MySQL 5.7 与 8.0 差异大（如默认引擎细节、窗口函数），学习资料先核对版本。
5. **忽视业务语境**：高可用/分库分表是权衡题不是标准答案，脱离业务规模和 RPO/RTO 谈方案没有意义。
