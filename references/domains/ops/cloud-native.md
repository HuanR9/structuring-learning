# 容器与云原生细分模块

> 领域模块六节 Schema：领域画像 / 细分路由 / 预设知识骨架 / 权威信源清单 / 进阶检查点 / 常见误区。

## ① 领域画像

容器与云原生关注应用的标准化交付与弹性运行：容器化、Kubernetes 编排、GitOps 发布、可观测落地。核心价值是**"一次构建，到处运行"**——把环境差异关进镜像，把发布流程变成代码。

## ② 细分路由

本模块即最小细分单位，不再下分。服务网格 / Serverless 作为 L5 认知分支，深入需另开模块。

## ③ 预设知识骨架

建模（P2）以此树为起点，按用户目标层级裁剪（规则见 `references/core/modeling.md`）。每个叶子节点括注掌握证据。

```
容器与云原生
├── L1 容器基础
│   ├── Docker 核心机制（镜像分层/容器运行时/仓库，能解释一条 Dockerfile 指令的影响）
│   ├── 镜像制作最佳实践（多阶段构建、层缓存、瘦身与安全扫描）
│   └── 容器网络与存储（bridge/overlay、volume 挂载语义）
├── L2 K8s 核心概念
│   ├── 集群架构（Master/Node/各组件职责，能画架构图）
│   ├── 工作负载（Pod/Deployment/StatefulSet/DaemonSet 选型）
│   ├── 服务发现与网络（Service/Ingress/CoreDNS，能说清一次集群内访问的路径）
│   └── 配置与存储（ConfigMap/Secret/PV/PVC，Secret 的安全边界）
├── L3 K8s 运维
│   ├── 调度与资源（requests/limits、QoS、亲和与污点）
│   ├── 发布策略（滚动/蓝绿/金丝雀的实现与回滚）
│   └── 排障（CrashLoopBackOff/Pending/OOMKilled/ImagePullBackOff 的定位套路）
├── L4 可观测与治理
│   ├── 监控（Prometheus Operator 与核心指标）
│   ├── 日志与事件（采集方案、Events 解读）
│   └── Helm 与 Operator（包管理、声明式运维认知）
└── L5 CI/CD 与生态（可选分支）
    ├── 流水线与 GitOps（ArgoCD/Flux 的拉模式）
    ├── 服务网格认知（Istio 的能力与代价边界）
    └── Serverless 认知（适用场景与冷启动代价）
```

## ⑤ 进阶检查点

| 阶段 | 能力证据（能做成这些即过关） |
|---|---|
| 初级（L1–L2） | 把一个含数据库的应用容器化并部署到 K8s（含配置与存储）；讲清 Pod 一次创建到 Running 的全过程 |
| 中级（L3–L4） | 设计一套工作负载的完整发布策略（含回滚演练）；独立定位一次 CrashLoop/OOM 故障；搭建集群级监控看板 |
| 高级（L5） | 设计 GitOps 发布体系；给出一个生产集群的治理方案（配额/网络策略/镜像安全） |

## ⑥ 常见误区

1. **只会 docker run 不懂 K8s**：容器只是起点，编排、调度、治理才是云原生主体。
2. **复制 yaml 不理解字段**：不读 API 文档的部署等于碰运气，版本升级就崩。
3. **忽视 requests/limits**：不设资源边界，一个Pod 打爆整个节点。
4. **镜像能跑就发布**：不做多阶段瘦身与漏洞扫描，镜像巨大且带隐患。
5. **版本差异凭经验**：K8s 小版本间 API 与默认行为差异真实存在，资料先对版本。
