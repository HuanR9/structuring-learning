# 应用安全细分模块

> 领域模块六节 Schema：领域画像 / 细分路由 / 预设知识骨架 / 权威信源清单 / 进阶检查点 / 常见误区。

## ① 领域画像

应用安全（AppSec）关注在软件设计、开发、测试与维护过程中识别并降低安全风险。学习以威胁建模、设计控制、代码审查和授权测试为主线；默认聚焦 Web/API 服务，移动端安全按用户目标关联移动研发或专项标准。

## ② 细分路由

本模块即当前应用安全入口。目标若仅为合规条文，转法律类数据合规；目标若聚焦云平台身份、基础设施配置或集群加固，转云与容器安全；渗透测试必须限定在明确授权的靶场或系统。

## ③ 预设知识骨架

建模（P2）以此树为起点，按用户目标层级裁剪（规则见 `references/core/modeling.md`）。每个叶子节点括注掌握证据。

```
应用安全
├── L1 安全基础
│   ├── 安全属性与风险（机密性、完整性、可用性、威胁、弱点、影响；能针对一个应用资产绘制简化风险场景并区分威胁与漏洞）
│   ├── 信任边界与威胁建模（数据流、身份、入口、资产；能为一个 Web/API 功能画数据流图，标出信任边界并排序主要威胁）
│   └── 身份认证与访问控制（认证、授权、会话、最小权限；能审查一个接口权限矩阵并用正反例验证越权边界）
├── L2 常见应用风险
│   ├── 输入与输出处理（注入、编码、校验、反序列化；能在授权测试应用中复现一种输入处理缺陷并验证修复）
│   ├── Web 与 API 风险（访问控制、认证、业务逻辑、资源滥用；能按 OWASP 相关清单检查一个 API 并记录可复现证据和影响）
│   └── 数据与密码学使用（敏感数据分类、传输/存储保护、密钥管理；能审查一个数据流的保护措施并指出密钥暴露或过度收集风险）
├── L3 安全开发生命周期
│   ├── 安全设计与依赖治理（安全需求、组件风险、更新策略；能为一个功能写出安全需求和依赖更新决策记录）
│   ├── 安全编码与代码审查（安全 API、错误处理、秘密管理；能对一段示例代码提交问题、风险和最小修复建议）
│   └── 自动化安全测试（SAST、DAST、SCA、模糊测试的适用边界；能为一个隔离样例配置至少一种扫描并复核误报与漏报）
└── L4 验证与治理
    ├── 安全验证标准（OWASP ASVS 等要求与等级；能为一个应用选择适当验证范围并把需求映射到可检查项）
    ├── 渗透测试流程与授权（范围、规则、证据、报告、复测；能为靶场演练写授权范围和停止条件并交付可复测报告）
    └── 漏洞修复与复盘（严重度、缓解、修复验证、根因改进；能为一个模拟漏洞安排修复优先级、回归验证和防复发措施）
```

## ④ 权威信源清单

| 级别 | 信源 | 备注 |
|---|---|---|
| 标准 | [OWASP ASVS](https://asvs.owasp.org/) | Web 应用安全控制的验证标准；当前稳定版为 5.0.0，使用时注明版本与条款号 |
| 官方项目 | [OWASP Top 10](https://owasp.org/www-project-top-ten/) 与 [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/) | 风险认知和实现建议；按项目类型与当前版本核对 |
| 官方项目 | [OWASP API Security](https://owasp.org/www-project-api-security/) | API 风险及测试背景，按发布版本使用 |
| 政府指南 | [NIST Secure Software Development Framework](https://csrc.nist.gov/Projects/ssdf) | 安全开发过程参考，不是单一产品的配置手册 |
| 实践环境 | OWASP Juice Shop、WebGoat 等明确授权的本地靶场 | 仅用于隔离练习；真实目标需另行获得明确授权 |

## ⑤ 进阶检查点

| 阶段 | 能力证据（能做成这些即过关） |
|---|---|
| 初级（L1） | 为一个功能画数据流与信任边界，列出主要威胁和访问控制规则 |
| 中级（L2–L3） | 在本地靶场完成风险复现、修复与回归，并说明自动化扫描无法覆盖的部分 |
| 高级（L4） | 为一个应用定义基于风险的验证范围，交付授权测试报告、修复排序和复测结果 |

## ⑥ 常见误区

1. **把 OWASP Top 10 当完整安全标准**：它用于风险认知，不替代系统化验证要求和威胁建模。
2. **把扫描器结果当漏洞结论**：自动化发现需人工复核上下文、可利用性和实际影响。
3. **把渗透测试等同于 AppSec**：测试是验证手段之一，不能替代设计、编码、依赖治理和修复闭环。
4. **忽视业务逻辑和权限组合**：单个接口看似安全，跨角色或跨流程仍可能出现越权。
5. **未获授权就测试真实系统**：练习和验证须在授权范围内进行，先确认范围、时间窗和停止条件。
